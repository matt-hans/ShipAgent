# Source reservation ownership fence: metadata-only first slice

Status: independently reviewed design with a local internal implementation candidate. Baseline is merged main `533eca6bf70cdd78fdb9b5fc86ef838d4ea57bee`. Scope follows #79 and ADR 0009, the preserved ingress contract, and independent ownership/transaction review. Milestone #79 remains incomplete. The historical 47 RED missing-feature cases remain historical evidence; the CSV package exists through #89, but a production ingress service does not. The accompanying plan records staged qualification; this design alone is not a release or deployment claim.

## Intent and first observable outcome

A separately authorized synthetic operator can reserve bounded metadata for a future source in an existing owned conversation, and recover that exact reservation by the same scoped request key. The operation resolves current authority and conversation ownership under exclusion, persists before acknowledging, and never creates usable source content. This isolates the authority/transaction composition before streaming, worker isolation and byte retention are added.

No completed Source Reference, receiver, parser invocation, row storage, source reader, mapping, active-source selection, model call, HTTP route, public tool or production adapter is added. There is no claim of working upload acceptance. Existing run history and conversation revision/state are never changed by this slice.

## Components and ownership

1. A real one-shot borrow token pins the existing CoordinatorLease lifetime before any store transaction. A short shared state mutex protects borrow admission/count and closing state; it is never held for database work. The owning AgentRunService marks borrow admission closing at the start of close, before any provider-cleanup await. This is a separate non-waiting begin_close marker, not an early descriptor close; existing provider cleanup still runs. New borrows then fail. is_owned/require_owned continue to describe actual physical ownership, including during closing, so admitted cleanup does not lose its ownership proof. A close attempt with live borrows returns unavailable promptly without unlocking or closing the descriptor. Admitted operations may finish and retire; a later explicit owner close releases the lease. Token retirement is one-shot and occurs only after actual context retirement. The exact admitted token has positive retirement_completed evidence only when its weak identity marker exists and active membership is absent. The weak admitted-token registry is populated under the short admission lock before exposing the token. Failed admission removes the weak marker before active membership, so it gains no completion proof. Retirement only removes active membership; interruption leaves either an active token that can quarantine or positive completion evidence. Unadmitted or copied tokens cannot gain this proof, and weak markers do not retain token tombstones. An operation can recognize complete retirement after an interruption only when every captured context and the final proven token have actually retired; this cleanup evidence grants no authority. Copied source coordinators reject by PID before entering their state mutex. The source component cannot close the owner’s lease. A borrow may set a separate sticky source-borrow quarantine on that exact lease. Quarantine rejects new source borrows and is checked by all admitted source operations after waits and before a new source commit/receipt; ordinary closing still permits admitted operations to finish. Physical ownership and existing model cleanup semantics are unchanged. A new Python coordinator cannot clear quarantine; recovery requires actual retirement, explicit owner close, a fresh lease/current generation and verified store reopen.
2. A narrow `AgentRunStore` borrowed-conversation-fence method opens its existing verified database and acquires `BEGIN IMMEDIATE`. It requires the already-owned matching CoordinatorLease and expected current generation. It does not create/replace a coordinator, advance generation, recover work, start a provider or return private history. Its connection remains owned by the operation until retirement.
3. A target-private reservation store uses a separate verified SQLite database pinned to the same account and exact target, with explicit initialization. Construction validates/allocates without I/O. Explicit open is single-attempt under a supplied deadline and retains its setup scope before acquisition; failed open never enables transactions or retries initialization. Explicit close retries retained setup cleanup, preserving known commit evidence and leaving operation-owned transactions alone. Reopening after failure requires actual cleanup and a fresh store object. It contains only bounded reservation metadata and ownership/schema metadata. Its private-file, sidecar and durability checks reuse the existing target storage pattern. Opening without explicit create does not initialize a missing store. Setup and transaction acquisition inspect only file/schema/owner identity; reservation rows are read and validated only during post-authority lookup/insert. The current coordinator generation fences each operation; it is not part of a reservation’s immutable ownership namespace, so an explicitly restarted coordinator can recover the same valid record without changing its identity or expiry.
4. One reservation operation coordinator owns both database contexts and the authority scope, including explicit commit and reverse-order retirement. Neither database wrapper may implicitly defer a write commit until after authority is released.
5. The operation coordinator has an explicit trusted expected target-key fingerprint supplied by local target setup, separate from operator/model inputs and separate from the authority response. It compares the resolved fingerprint to that pin before any reference-dependent lookup. A changed key requires a new explicitly configured coordinator; no automatic pin update or old-reservation rebind occurs. This is only synthetic configuration here, not enrollment/key-possession qualification.
6. `SourceAuthority` is constructor-injected and absent by default. No production adapter is supplied. A current callback returning `True`, caller DTO or copied reference is not accepted as an equivalent fence.

The product interface separates an operation request/selector from authority. A trusted adapter may supply an operator principal reference and selected Provider Connection ID; those values alone prove nothing. The authority implementation resolves current records under its fence. It supplies account, current non-null opaque epoch, exact target/key identity, permitted operation purpose and the original expiry of its operator authorization. Acquisition does not renew that authorization; it is rechecked after waits and before commit/response alongside the conversation/reservation expiry. The coordinator obtains conversation fields itself from the already-held Agent Run connection and checks the complete binding against its pinned target/account.

No caller or model argument may choose epoch, fingerprint, authority implementation or coordinator generation. A future transport must establish operator authentication and purpose before creating the request context; this slice supplies no transport or token parser.

## Closed operation policy

Both `reserve` and `recover` require the same closed operator-source-setup purpose in this first slice. Provider preview/status scopes alone are insufficient. No separate provider-readable status surface is introduced. A test principal may be enabled only through the disposable fixture's trusted setup; it is not real authentication evidence.

Reservation admission and recovery require an existing conversation owned by the resolved account/connection/epoch and exact target, with a live original expiry and state `waiting_for_input`. Legacy NULL-epoch, unknown, foreign, active, completed, failed or cancelled conversations are unavailable in this deliberately narrow profile. This avoids implying useful attachment before conversation creation or while a model turn is active. A later reviewed source lifecycle may broaden eligibility.

Creating a reservation does not answer or consume the clarification. If ordinary continuation later changes the conversation, the old reservation binding and expiry remain immutable. Recovery is unavailable while the conversation is ineligible; if the same conversation later legitimately waits again under the same binding and original lifetime, recovery can describe the same historical reservation. It cannot select a source or authorize a turn. The admitted conversation revision is retained privately for audit, not treated as a transferable revision grant.

All foreign, unknown, revoked, wrong-purpose, wrong-target/key and unavailable-authority cases share a fixed unavailable error before conflicts or expiry are revealed. An authorized same-binding expired reservation returns a fixed expired error. No errors/logs include supplied identities, hashes, metadata or exception details.

## Transaction and lock order

Every reservation operation has exactly this order:

1. Acquire the live lease borrow token; obtain the Agent Run writer reservation.
2. Obtain the source reservation-store writer reservation.
3. Acquire the authority fence, with a bounded acquisition deadline.
4. Resolve current authority. Only then query the conversation and reservation/idempotency identity on the already-held connections.
5. Recheck the live lease/file identity, current coordinator generation, complete binding, conversation eligibility and original expiry after the waits.
6. Materialize the bounded operation result; recheck deadline/expiry immediately before a write commit. Call the actual source-store commit while both writer reservations and authority exclusion remain held.
7. Retire authority, source and Agent Run contexts in reverse order, then retire the borrow token exactly once. The Agent Run transaction is logically read-only and makes no conversation mutation. A cleanup exception cannot be hidden by an unconditional finally that retires the token: uncertain retirement retains the original contexts and token in the unavailable coordinator until explicit successful retirement/reconciliation.

This matches existing Agent Run → authority callbacks. Neither authority acquisition nor invalidation may acquire an Agent Run or reservation-store lock while holding the authority fence. Resolver code cannot re-enter store methods. No network request, receive loop, parsing or arbitrary caller callback runs under these reservations. A WAL read snapshot alone is not the conversation fence.

There is no atomic-write claim across two databases: only the source store writes. The Agent Run writer reservation prevents conversation changes while that write is decided and committed. All paths, including recovery/inspection and maintenance introduced later, must obey the same order.

## Concrete synthetic authority exclusion

The qualification fixture uses a dedicated disposable SQLite authority database and holds `BEGIN IMMEDIATE` through the operation. Trusted fixture mutations use the same writer reservation. Cross-process tests start fresh process-owned leases/connections; copied or fork-inherited Python borrow state is never treated as shared coordination. Borrow tokens are confined to their creating process. This gives an actual separate-connection/process exclusion mechanism rather than an independently checked boolean. Authority mutations never call either product store.

The fixture records current operator purpose/account/connection, non-reusable epoch, target/key identity and enabled status. Its rows are populated only by test setup. Mutation and reservation races must prove both orderings across actual connections/processes. No Auth0 revocation, target possession, relay delivery or held headless publication scenario is inferred from this fixture.

Production remains unavailable without a separately reviewed adapter providing equivalent exclusion. A cached target record or a lease that expires and drops exclusion while a delayed commit continues is insufficient.

## Linearization, deadlines and retirement

A successful source-store commit is the reservation publication point. If the deadline or original expiry passes during commit, preserve the known committed record and capacity, but do not acknowledge a new live reservation. Return a fixed unavailable/expired outcome as applicable, and reconcile only the original key under fresh authority. A later valid retry can recover the same record; it cannot renew an expired one. If invalidation wins the authority fence first, the operation cannot publish or recover authorized metadata. If publication wins first, later invalidation blocks subsequent operations; it does not erase the record or retract a result already materialized under authority.

Recovery materializes its complete bounded receipt while all fences are held and tests expiry again before returning it. No cursor, iterator, active transaction, reusable authority object or private reader escapes. The receipt is descriptive data, never authority for a later operation. A result delayed in transit may be stale; a subsequent operation must acquire fresh authority again.

Acquisition uses one monotonic operation deadline, initially two seconds in the synthetic profile, with remaining-budget SQLite busy timeouts rather than three independent reset budgets. This budget starts before borrowing/opening and is propagated into connection opening, identity/schema checks and potentially busy PRAGMA/BEGIN steps, not only BEGIN IMMEDIATE. The existing AgentRunStore connection path currently has a fixed three-second timeout; the new borrowed path must take the remaining deadline while leaving unrelated callers’ defaults unchanged. Foreign database identity must still be rejected before journal-mode changes. The deadline is checked after each wait and before commit/response. The trusted UTC clock sets immutable persisted expiries; rollback of system time and storage backups are separate unqualified operational cases. No periodic poll renews a deadline or expiry.

The authority database lock does not expire by itself. A timeout aborts before publication when possible, but the coordinator must retain ownership until rollback/close actually retires the contexts. Any uncertain release, cleanup failure or ambiguous commit latches this reservation coordinator unavailable and quarantines source borrowing on the shared lease. It may not admit a new operation or pretend to forcibly terminate a stuck in-process filesystem/adapter. A hard wall-time guarantee under hostile storage is not claimed. All qualification jobs remain externally supervised.

An ambiguous COMMIT or retirement failure preserves the exact scoped request identity and original recorded outcome evidence, and latches admission unavailable. It must not report rollback as proven, remint automatically, use a different key, or release capacity based only on an exception. After explicit verified store/lease recovery, reconcile that same identity under fresh authority: return the existing reservation if present and valid; fail closed on conflicting/corrupt/uncertain state. If rollback is proven and no reservation was ever committed, a subsequent explicit reserve is an unaccepted retry, not resurrection of an acknowledged reservation. Failure after a known successful commit must retain that known evidence even if the response cannot be delivered.

## Metadata, identity and bounded retention

The idempotency namespace is exactly account, Provider Connection, epoch, conversation, exact target, target fingerprint, operation `upload`, and request-key text. Input identity covers declared byte length, lowercase SHA-256, normalized `text/csv` and the fixed parser-profile version. Bounds and validation reuse the CSV primitive's constants where applicable; there are no content bytes to parse.

An identical request recovers the same private reservation ID and original times. Changed normalized input in the same currently authorized namespace conflicts. Another namespace cannot recover or infer that record. Request-key and opaque epoch text are 1–128 characters and at most 512 UTF-8 bytes. Other resolved identity/selectors are nonempty and at most 256 UTF-8 bytes, while the conversation reference must satisfy the existing canonical Conversation ID grammar. Control characters and invalid Unicode are rejected with a closed error. Declared length is a non-bool integer from 1 through the parser’s 1 MiB cap, digest is exactly 64 lowercase hexadecimal characters, and media/profile strings are exact constants. These bounds admit the existing account/connection/target identifiers; they do not normalize or reinterpret identity text.

Admission records one original upload expiry, at most five minutes and capped by the conversation's original expiry. It also records the prospective source expiry, at most 24 hours from that same admission and capped by the conversation, solely for later compatible lifecycle review. No usable source or source lifetime grant is created now. Retries never reset these times. `now >= expiry` is expired.

Reservation IDs stay target-private and independently random. Do not reuse canonical INGRESS/INPUT identities or expose an invented public `source_reference`. A future public Shipment Source family needs its own canonical registry/schema review.

At most 1,024 retained records, including expired reservations, and at most 4 MiB of actual encoded bounded metadata are permitted. A changed-input conflict does not create another record or alter the original. At most two unexpired reservations may be live per target, as a conservative metadata policy aligned with the preserved future limit; this does not qualify concurrent transport uploads. Identical recovery does not consume another slot. Admission fails before insertion would exceed any of these caps. No pruning, background cleanup, reference recycling or automatic deletion is introduced, and expired rows still count. Each private record uses versioned canonical UTF-8 JSON with sorted fixed keys, compact separators, ensure_ascii=False and allow_nan=False; no dynamic extra fields are accepted. The logical accounting includes the actual JSON byte length plus the encoded lengths of separately persisted ID/index/digest fields and fixed per-row scalar fields. One record is capped at 8 KiB. Neither the parser’s normalized-byte counter nor a Python object size is used as this persisted-metadata measure. The schema/accounting function and both byte/count boundaries must be tested explicitly. SQLite page/WAL overhead is separately reported; this logical metadata cap is not presented as a complete physical disk quota. Physical/WAL accounting is a mandatory later gate before any byte/blob publication or operational ingress claim.

## First-slice acceptance and explicit deferrals

Required now: correct reservation/recovery and changed-input conflict; both invalidation ordering outcomes; wrong/missing identity/purpose and NULL epoch; actual writer contention; conversation cancellation/continuation versus admission; lease/generation/file-identity loss; borrow versus concurrent close/commit, rejection during owner shutdown, one-shot retirement and retained borrow after uncertain cleanup; expiry after every wait and before response; no use after scope retirement; acquisition timeout; commit-unknown and known-commit/failed-retirement reconciliation; two coordinator instances cannot bypass the shared sticky quarantine; process-crash recovery of metadata identity; metadata/record caps; no model/provider construction, imported bytes, new files outside owned test stores or runtime effects.

Later: upload tickets as transport capabilities, bounded transit-only reception, incomplete-stream handling, parser process/resource ownership, content/physical/WAL quotas, raw/normalized encoding and checksums, immutable blob publication/readers, cleanup/tombstones, public source family, model-safe schema/mapping, source selection/run pinning, operator HTTP/CSRF, production epoch/key adapters, real clients and deployment. None of the preserved contract's deferred acceptance cases becomes a skip or pass for this narrower slice.

The written design and serial plan were independently reviewed before implementation. Final candidate review, fresh remote full regression, CI and merged-main checks remain separate release gates. Production authority, content ingress and the other explicit deferrals above require later reviewed slices; this document does not qualify them.
