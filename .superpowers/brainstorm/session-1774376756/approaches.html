Three Approaches for the Angular Module Federation Rebuild

Same decisions, different execution strategies. Click to select your preferred approach.

A

Big Bang Rebuild

Build the entire Angular app, then swap it in.

Create the full Nx workspace with all 4 remotes + shell + shared libs from scratch. Develop in parallel with the React app. When feature parity is verified, switch Tauri/Docker to serve the Angular build.

Pros

  • Clean architecture from day one — no migration hacks
  • React app stays stable during development
  • Can rethink patterns that don't translate well
  • Team can build idiomatically Angular, not "React in Angular"

Cons

  • Longest time before any Angular code is in production
  • Feature drift — React app evolves while Angular catches up
  • All-or-nothing cutover risk
  • Duplicate maintenance during overlap period
Timeline: Build all → Verify parity → Switch
B

Strangler Fig (Incremental Migration)

Replace one remote at a time inside a hybrid shell.

Build the Angular shell first, embed the React app as a "legacy" remote via iframe/web component. Then replace one module at a time: Shared → Settings → Sidebar → Chat. Each swap is a deployable milestone.

Pros

  • Incremental value — each module ships independently
  • Lower risk — rollback one module, not everything
  • No feature freeze on React during migration
  • Teams can onboard to Angular gradually

Cons

  • React↔Angular bridge complexity (events, state sync across iframe)
  • Two frameworks in production simultaneously — double the bugs to triage
  • Performance overhead from iframe/web component boundary
  • Hybrid state is messy and hard to reason about
Timeline: Shell → Settings → Sidebar → Domain → Chat (one at a time)
C

Foundation First, Remotes in Waves

Build the Nx scaffold + shared libs first, then build remotes in parallel waves.

Phase 1: Nx workspace, shell app, shared libs (state, API, SSE, design system, types). Phase 2: Build all 4 remotes in parallel against the shared contracts. Phase 3: Integration, Tauri hookup, parity verification. No hybrid — pure Angular, but structured for parallel team execution.

Pros

  • Clean architecture — no migration bridges
  • Shared contracts defined first — teams can work independently
  • Parallel remote development (4 teams/tracks at once)
  • Fastest path to full parity with multi-team model

Cons

  • Foundation phase blocks all remote work (must be solid)
  • Still a full rewrite — React app frozen during build
  • Shared lib API may need revision once remotes start building
⟵ RECOMMENDED   Timeline: Foundation → Parallel remotes → Integration → Switch

Why I recommend C

You said the move is about supporting multiple teams. Approach C is designed for exactly that — the foundation phase defines the contracts (shared state, API service, SSE service, design tokens) that let teams build remotes independently without stepping on each other. Approach A is similar but doesn't emphasize the parallel execution model. Approach B adds bridge complexity that defeats the purpose of a clean rebuild.
